# 开发笔记

> 记这个项目里真正花了时间才想明白的问题:为什么这么设计、踩过什么坑、还剩什么限制。
> 用法看 [README](../README.md)。

## 一、几个设计取舍

**1. 小库用全量注入,不做检索。**
示例库 7 张表 / 34 列,schema 全文塞进 prompt 也就几百 token。相比引入向量库 + 混合召回 + 阈值调参,全量注入更简单、更准,也更容易复现。检索是表数量上去以后的问题。

**2. 校验用 AST,不用正则 / 字符串黑名单。**
黑名单挡不住注释、大小写、子查询里的危险函数。用 sqlglot 解析成 AST 之后,「只允许 Select 形态 / 表白名单 / 联表数上限 / 危险函数 / 列名是否存在」都能在结构上判断,而不是在文本上猜。

**3. 校验产物就是执行物。**
校验通过后返回的 `final_sql`(可能被兜底改写过,比如补 LIMIT)才是执行器的输入。否则会出现"校验的是原 SQL、执行的是改写后的 SQL"这种漏检。

**4. 只读连接是最后一道防线。**
AST 只能保证结构上不危险 —— `SELECT ... INTO OUTFILE`、`FOR UPDATE` 这类都是 Select 形态,拦不住语义。所以真正的写入拦截放在权限层:SQLite 用 `mode=ro` URI,MySQL 用只读账号。

**5. 方言:能解析 ≠ 能执行。**
模型更熟 MySQL,经常在 SQLite 场景写 `DATE_FORMAT` / `CONCAT`。sqlglot 会把它们当未知函数原样保留,解析照样"成功",等到执行才炸。
所以 `ensure_dialect` 不只是 parse → 输出:解析成功后还会再探一次 AST,残留 MySQL 专属函数就当 MySQL 重转译,AST 干净才用目标方言输出(顺便保住 `||` 不被 MySQL 解析器读成 `OR`)。

## 二、踩过的坑

1. **列校验在表别名下失效** —— 多表 SQL 几乎必用别名,`o.total_amount` 拿真实表名查不到,校验形同虚设。修法:建「别名 → 真实表」映射。
2. **M-Schema 的枚举 / 外键没进 prompt** —— 设计上写了"必须喂给模型",代码只渲染了列名和类型。修法:`format_m_schema` 显式输出 `取值:` 与 `外键:`。
3. **注释里的全角冒号** —— `会员等级：普通,银卡` 用半角冒号截断会漏,逗号会污染 M-Schema 结构。修法:半角 / 全角都处理。
4. **schema 缓存只看文件 mtime** —— 解析器升级后源文件没变,缓存永远不会刷新,拿到旧结构。修法(待做):指纹里加 `parser_version` 或直接改用内容哈希。
5. **`_meta.source` 写绝对路径** —— 产物是要提交的,绝对路径等于把本机目录结构发出去。修法:写相对仓库根的路径。
6. **SQLite 没有服务端超时** —— MySQL 可以加 `MAX_EXECUTION_TIME` hint;SQLite 只能用 `progress_handler` 主动中断,所以 `with_timeout` 必须按方言跳过。
7. **大笛卡尔积测不出超时** —— SQLite 会把纯跨表 `COUNT(*)` 乘算优化掉(177³ = 5.5M 行只用 0.04s)。要测超时得换无终止的递归 CTE。
8. **只读连接下不能建表** —— 需要建临时表的用例必须用普通连接,不能用 `mode=ro`。

## 三、已知限制

- **截断探针会被注入的 LIMIT 挡住**:校验器给无界明细补 `LIMIT 1000`,引擎拿到手就只有 1000 行,永远探不到第 1001 行 → `truncated` 一直是 False、`total` 等于 LIMIT 值。修法:注入 `DEFAULT_LIMIT + 1`。
- **sqlglot 的 sqlite 生成器不完整**:`NOW()` 原样输出(SQLite 没有该函数),`YEAR()/MONTH()/DAY()` 不会转成 `STRFTIME`。目前靠 prompt 声明方言规避。
- **混合方言有取舍**:一条 SQL 里同时出现 MySQL 函数和 `||` 时,按 MySQL 重解析会把 `||` 读成 `OR`。
- **schema 指纹是 mtime**:git checkout 会改 mtime,缓存因此失效并重抽。
